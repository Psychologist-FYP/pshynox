Which model should we use?

A model and its runtime are different things: Whisper small is the trained speech model; faster-whisper and whisper.cpp are implementations that run it.

| Candidate | Proposed use | Main trade-off |
|---|---|---|
| Multilingual Whisper base | Lightweight baseline and fallback | Lower resource requirements; accuracy must be checked |
| Multilingual Whisper small | First serious candidate | Reasonable starting balance of model size and quality |
| Whisper medium | Later quality comparison | More processing time and memory |
| Whisper large-v3 / turbo | Optional later experiments | More demanding; avoid making the MVP depend on them |

Use multilingual names such as small, not small.en, because your project includes Urdu and English. Whisper’s published results vary substantially across languages, so English performance cannot establish Urdu or mixed-language quality. Official Whisper documentation.

My proposed runtime choice is:

- First implementation: faster-whisper. It fits the existing Python backend and provides segment timestamps, CPU INT8 execution, and integrated Silero voice activity detection. Its PyAV dependency handles audio decoding using bundled FFmpeg libraries. faster-whisper documentation.
- Comparison runtime: whisper.cpp. Your implementation plan specifically recommends benchmarking it. It supports quantized models and is a useful portability candidate. We should compare the same recordings and model sizes before choosing the deployment default. whisper.cpp documentation.

INT8 quantization uses a lower-precision representation to reduce resource requirements. Whether its quality and speed are acceptable needs measurement on your recordings.

How we should implement it

1. Prepare a small evaluation set first.
   Record several fictional 2–5 minute conversations: English, Urdu, and mixed Urdu–English. Write manually checked reference transcripts. Include silence, quiet speech, background noise, and some interruptions. Keep separate recordings or speakers for final evaluation.
2. Build a standalone transcription baseline.
   Start with WAV input and run base and small on the same clips. Download model assets during setup, then load them from local paths. Verify that inference works with networking disabled.
3. Add reliable audio preparation.
   Validate missing, empty, corrupt, and unsupported files. Convert to the model’s required audio representation, typically 16 kHz mono for this baseline. Preserve the original recording; if two microphone channels are introduced later, preserve those channels for speaker work.
4. Add speech detection and timestamp handling.
   Voice activity detection identifies speech regions so we can avoid processing long silences unnecessarily. Crucially, timestamps must still refer to the original recording, even when silence is skipped. Begin with segment timestamps; precise word alignment is a later enhancement.
5. Adapt output to the existing contract.
   Each segment must contain id, session_id, start_ms, end_ms, speaker_role, text, and revision. Initially use speaker_role="UNKNOWN". Preserve IDs when users correct text or speaker labels.

   A sensible proposed interface is:

   transcribe(audio_path, *, session_id, config) -> list[TranscriptSegment]

   The integration guide leaves session-ID binding open, so this interface should be coordinated with Talha before integration.
6. Integrate through Module C’s job workflow.
   Run inference outside the web request’s main execution path and process one heavy job at a time initially. Module C validates and saves the output, exposes success/failure status, and handles corrections. Missing models or processing failures must produce explicit errors.
7. Evaluate, document, and harden.
   Add contract/error tests, real-model smoke tests, installation instructions, pinned dependencies, model/license information, and a benchmark report. Then extend testing to 15-minute and eventually 45–60 minute recordings.

The two hardest parts deserve separate treatment

Urdu–English switching: multilingual support does not guarantee accurate switching within a sentence. We should test automatic language detection and explicit language settings on representative clips. Use transcription rather than translation, and agree on reference text conventions—particularly Urdu script versus Roman Urdu—before calculating accuracy.

Speaker identification: transcription answers “what was said”; diarization answers “who spoke when.” Even a diarization system normally produces speaker identities, not reliable CLIENT/CLINICIAN roles. Start with manual correction, as your Week 2 plan allows. Later, evaluate two-channel recording or automatic diarization separately. Two microphones can still capture both speakers.

Also, retain original timing information if you later calculate pauses or speaking rate. Removing silence must not erase the measurements that feature needs.

When can we call Module A complete?

For the Week 2 MVP, it should:

- Transcribe a 2–5 minute fictional WAV offline.
- Return valid segments with usable timestamps.
- Allow the integrated app to save, reopen, and correct them.
- Handle invalid audio and missing models clearly.
- Include actual processing-time measurements.

For the finished module, add reproducible installation, language-specific accuracy results, long-recording benchmarks, documented limitations, and integration tests.

Use word error rate and character error rate, plus manual inspection of omissions, negations, names, and timestamp accuracy. Measure processing speed as:

Real-time factor = processing time ÷ recording duration

For example, 2 minutes to process 5 minutes of audio gives 0.4. That is an illustration, not a measured result for your laptop.

The first step should be a small benchmark of multilingual base and small on your laptop. That will tell us whether small offers enough accuracy at an acceptable speed, and give us evidence for the implementation choice before we build the full pipeline.
